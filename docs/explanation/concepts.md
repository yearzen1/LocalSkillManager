# 核心概念：作用域、身份与分组

这篇文档解释 `lsm` 的几个设计选择：为什么只有 global 和 project 两个作用域、为什么目录名就是 skill 的身份、为什么 pull/push 是复制，以及分组为什么放在全局配置里。它不负责教你操作；需要动手时按文末链接转到指南或教程。

## 背景

agent skill 的事实来源是 `.agents/skills/`。一个 skill 是一个目录，目录里有 `SKILL.md`，还可能带脚本和资源。`lsm` 只维护这一份目录，不代理其他 agent 的私有目录。

当 skill 同时存在于「全局」和「项目」时，需要回答三个问题：

1. 哪个副本是权威的？
2. 项目里的副本从哪里来、如何更新？
3. 常用的一组 skill 如何复用？

`lsm` 的答案分别是：目录名即身份、pull/push 复制、分组保存为全局偏好。

## 两个作用域

| 作用域 | 位置 | 语义 |
|---|---|---|
| global | `<LSM_HOME 或 ~/.agents>/skills/` | 个人 skill 库，跨项目复用 |
| project | `<cwd>/.agents/skills/` | 当前项目实际使用的副本 |

`project` **固定为进程当前工作目录**，不会向上查找 `.git` 或 `.agents`。这是有意接受的取舍：

- 好处是实现简单、行为可预测，脚本里不需要猜项目根目录；
- 代价是在子目录执行命令会把 skill 装到子目录。

因此文档反复强调：请在项目根目录执行。

## 目录名即身份

`SKILL.md` 的 frontmatter 里也有 `name`，但真正决定身份的是**目录名**：

- 两者一致才算合法 skill；
- 不一致时 `list` 标记 `[invalid]`，`pull` / `push` 拒绝复制；
- 改名必须连目录一起改，避免同一个 skill 出现两个名字。

如果以 frontmatter 为准，目录名就只是任意容器，路径、重名和覆盖判断都会变得模糊。以目录名为准后，路径、前缀解析、覆盖目标都可以从名字直接推导出来。

## pull/push 是复制，不是链接

`pull` 把 global 的 skill 复制到 project；`push` 反过来。复制而不是链接，原因有三点：

- Windows 上符号链接需要额外权限，行为不可靠；
- 项目里的副本可能被修改，链接会让改动直接污染全局库；
- 复制后的项目可以独立运行，不依赖某台机器的全局目录。

代价是两边会分叉：`pull` 不会自动同步后续改动，需要显式再执行一次，并用 `--force` 决定是否覆盖。覆盖采用「先写临时目录、再整体换位」的原子方式，失败时旧目录保持完整。

## 为什么分组放在全局配置

分组是「我常用哪些 skill」的个人偏好，不是项目属性。把它放在全局 `config.toml` 的 `[groups]` 里，符合现有的一次性全局配置模型：

- 不引入项目级配置，避免「在子目录执行换了分组」这类新问题；
- 换项目时不需要重复定义同一套组合；
- 分组与语言共用同一份配置文件和同一套原子写入逻辑。

代价是分组不能随仓库共享，也不能表达「这个项目只要其中两个」的差异。需要项目级差异时，仍然显式执行 `lsm pull <name>...`。这个取舍记录在决策 Q53 与 Q57。

## 取舍一览

| 选择 | 得到什么 | 放弃什么 |
|---|---|---|
| project 固定 cwd | 行为可预测、实现简单 | 子目录执行会装错位置 |
| 目录名即身份 | 路径与覆盖目标可直接推导 | 改名要同时改 frontmatter |
| 复制而非链接 | 跨平台可靠、项目独立 | 两边可能分叉，需要显式同步 |
| 全局分组 | 跨项目复用、无项目级配置 | 不能随仓库共享，无项目级差异 |
| 分组惰性读取 | 写坏 `[groups]` 不影响其他命令 | `group` 与 `pull --group` 仍会因坏文件失败 |
